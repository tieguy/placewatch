## For your review

1. **Topic subscriptions ride only on the first account's pass** (Task 3, `dispatchEdit` with `topics: i === 0`). This is the smallest change, and SF's code path stays the same. The alternative: a separate topic pass that belongs to no account. It would be cleaner once there are more cities, but it means restructuring `sendStatus` and its single shared render.
2. **The reworked ranking scripts are not tested on real data before the Miami run** (Tasks 5–8). You chose not to re-crawl SF, so the only check that the rework kept the old behaviour uses a small made-up dataset: the old and the new `rank.js` must produce identical output on it. That catches a change in how `rank.js` ranks. It cannot catch a mistake that only real data shows, such as a `reassess.js` stage reading the wrong cache file or querying the wrong WikiProject. The first real run of the reworked scripts is the Miami run in Task 9. The alternative: re-crawl SF (about 18,500 articles) first to get a real baseline.
3. **A posted-log entry naming an unknown account stays active and is retried every sweep** (Task 2). Its post is never marked deleted while it might still be up. The alternative: mark the entry abandoned after N sweeps. That stops the repeated log line, but a post could stay up without anyone noticing.

Decided in review (2026-11-21): a problem confined to an account after the first, such as Miami's missing secret, disables only that account and logs a loud line at startup. SF keeps running (Task 1).

**Goal:** Run a Miami Bluesky account (`mia-wiki-top500.bsky.social`) as a second account in the existing sfedits bot, and make the link-based importance ranking region-generic so Miami gets its own ranked watchlist.

**Architecture:** Part 1 (Tasks 1–4) makes the bot safe for more than one account. Secrets are set per account. The posted log records which account posted, so one sweeper deletes posts with the right credentials. Each topic subscriber gets one post per edit, not one per account. A configuration problem in an account after the first disables that account and never stops the bot. Then Miami is added to `config.base.json`. Part 2 (Tasks 5–9) brings `scripts/rank.js` onto `integration` behind a fixture test that compares it with the original. It moves every SF constant of the ranking pipeline into region profiles (`regions/<name>.json`), adds `--region` to the scripts, and runs the pipeline for Miami. Part 1 and Part 2 touch no common files. They can run in either order.

**Tech Stack:** Node.js, mocha + chai + nock + proxyquire (`npm test`), minimist (already a dependency), m3api via `lib/mw-api.js`, Toolforge Build Service.

**Spec:** `docs/design-plans/2026-11-12-miami-bot.md`. The operator approved the version at `/home/louie/.plannotator/plans/miami-bot-a-second-account-and-2026-11-12-approved.md`. Task 1, Step 1 copies the approved version into the repo.

## Global Constraints

- The SF account (`accounts[0]`) must post exactly as today. Its envvar names stay `SFEDITS_BLUESKY_PASSWORD`, `SFEDITS_MASTODON_ACCESS_TOKEN`, `SFEDITS_DISCORD_WEBHOOK_URL` and `SFEDITS_INVITE_CODES`. SF gets no `id`.
- A push to `fork/integration` deploys within ~15 minutes. Push only after the operator approves. Tasks 1–3 must be safe to deploy with no Miami account in config.
- A configuration problem in an account after the first (a missing secret, or a missing, malformed or duplicate `id`) disables that account. The bot logs it with `console.error` at startup and keeps running. It never stops the bot (operator decision, 2026-11-21).
- Miami: account `id` is `"miami"`. The Bluesky handle is `mia-wiki-top500.bsky.social`. The secret envvar is `SFEDITS_MIAMI_BLUESKY_PASSWORD`. Bluesky is the only channel: Miami gets no `discord`, `mastodon` or `wikidata_claims` stanza.
- Miami edit filters are the same as SF's: `{ "bots": false, "minor": false, "substantive_only": true }`.
- Wikimedia requests go through `lib/mw-api.js` (scripts and bot) or `wm-fetch <url>` (ad-hoc checks). Requests are serial. Never use `Promise.all` against a Wikimedia host. `webfetch` is blocked for Wikimedia hosts.
- Do not change the incident-regression test `test/fan-out.test.js:104-146` ("never delivers a topic-only edit to the account's own platforms"). It must stay green.
- The SF ranking caches are not available. The refactor of the ranking pipeline is proven with a fixture test only, with no SF crawl (operator decision, 2026-11-12).
- The Miami ranked list replaces the WikiProject ratings only when the operator decides. This plan publishes the list and reports. It does not switch `titles_url`.
- The repo is not onboarded to SonarQube (it has no `.sonar-config.json` or `sonar-project.properties`). Per `AGENTS.md`, say so once at the first commit and offer onboarding.
